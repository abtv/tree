# Vim conformance matrix

This is a test inventory for the behavior specified in [PRODUCT.md](PRODUCT.md) §4.3 and §20.2. It does not define additional Vim behavior. “Covered” means that the named automated tests exercise the stated case; it does not claim that every possible key sequence is tested. The navigation dimensions follow [DEVELOPMENT.md](DEVELOPMENT.md) §8.

**Vim divergence.** A row marked **Vim divergence** states a behavior that deliberately differs from what Vim does for the same Normal-mode key or command; the reason after the marker explains the deliberate application model. The rest of a marked row remains a claim about Vim. A row without the marker is expected to match Vim for the keys and commands it names, so an unmarked divergence is a defect. Vim has no attachment or node tree: a row that names a Vim key is compared with Vim's result for the same keys applied to the node's text (and, for node commands, to the node tree), so behavior that reaches the attachment departs from Vim. A row without the marker is not a conformance claim when it describes only application mechanisms with no Vim key or command (application modifier shortcuts, pointer, blur, focus, and session bookkeeping, persistence and quit behavior, unsupported keys, and test coverage rows), or when it describes only the attachment's own caret state (an image caret, a saved return position, or an image-only node).

**Who decides a divergence.** The two directions are not symmetric. A divergence while editing text inside a node is a defect: fix it without asking and report it, because a Vim user must not be surprised by how ordinary text editing behaves. The behavior of commands that act on the tree, where Vim has no counterpart, is the Product Owner's choice even when one option looks obvious — this product has no precedent to copy — so propose the options and their reasons rather than choosing one. `PRODUCT.md` §1.1 records where Vim fidelity sits among the product's standing commitments.

## Interaction-state contract

This contract makes the existing [PRODUCT.md](PRODUCT.md) §20.2 behavior and its focus/caret test expectations explicit. It does not add commands or change state ownership. A transition's observable state is the selected node, Vim mode, focused input, text selection or image caret, and (when an image was entered from text) the text position to restore. The store's focus intent has a node ID, cursor, and monotonically new token; the token distinguishes an intentional focus request from an unchanged store focus after a local caret motion. The selected node ID alone cannot make that distinction.

| State or event | Contract |
| --- | --- |
| Normal text and image caret | Exactly one caret is active on the selected node. Text positions are character indices, with a block selection on the current text character. An attached image is the terminal character at `text.length`; on an image-only node, index `0` is the image and there is no text position to save. |
| Saved image return position | Same-node `j` from text and `l` from text into the image save a valid position in that node's text. `k` or `h` from the image restores it, with a remaining count applied for `h`. An in-node move to text, edit that lands on text, or cross-node move clears it. It never belongs to another node. |
| Focus intent | A successful store navigation, history operation, structural operation, or explicit selection supplies a fresh focus token, including when the selected node ID remains the same. The renderer applies its target cursor to focus and derives the image caret from the target node and cursor, superseding an older saved return. Local character motion changes the caret without a store focus request; an unchanged token must not replay an older focus cursor over it. |
| **Vim divergence:** a clamped whole-node Visual move reselects the node at text position `0`, where Vim's linewise Visual keeps its column (PRODUCT §20.2). No-op and clamped transition | An unavailable undo, redo, or leave and whole-node Visual entry followed by exit without movement produce no new focus intent, so the active image caret and saved return position survive. A failed in-node search leaves the caret in place. A level-boundary motion can explicitly reselect the same node with a new focus cursor; it must apply that cursor even though the node ID is unchanged. Clamped `k` on an image-only first root retains its image caret, while a whole-node Visual clamped move selects cursor `0` and clears a prior text-plus-image caret. |
| Modes and pointer input | Normal uses the text block or image caret; Insert and Replace use the thin text caret; character Visual and whole-node Visual own their selections. Escape and Visual exits resume Normal at the documented cursor. Pointer focus/selection preserves the current Vim mode and places the text caret at the pointer-selected position; leaving an image through pointer input drops the old saved return. A focus-changing application command during character Visual mode preserves the mode while dropping the pending command and endpoints, so it re-anchors like a pointer press; the same clear happens for `Cmd+A` and on any blur (a breadcrumb or enter-control click or another focus loss). Whole-node Visual mode's range is relative to the displayed level, so those commands and navigation clicks end it for Normal mode and clear the range, while a plain blur between node inputs (range extension) preserves it; `Cmd+A`'s full-text selection survives that exit. A pending Replace edit is committed before an application history, node-entry, node-leave, node-delete, select-all, cut, or paste command runs, whether triggered by keyboard or a pointer click (including the node's own enter control, whose `mousedown` handler otherwise suppresses the browser's default blur); a select-all, cut, or paste commits it without rewriting the DOM so the visible selection survives, and drops the pending command and character Visual endpoints while whole-node Visual's range stays intact. |

The store owns location and focus intent; the renderer owns mode, DOM caret/selection, image-caret indicator, and saved image return position. This is a characterization of the current architecture for the VIM-2 tests, not an implementation of the later transition model. Focused coverage for token-sensitive no-ops and same-node requests is in `src/application/editor-store.test.ts` and `src/renderer/use-node-input-bindings.test.tsx`; the rows below map representative Electron behavior.

## Insert and Replace completion policy

Insert and Replace sessions are mutually exclusive at any instant: Replace only starts from Normal mode with `R`, and unmodified keys never reach Vim command handling while Insert mode is active. Their completion needs differ by what they hold: Replace buffers typed text only in a ref and the DOM, so ending it without committing is data loss; a plain Insert session (`i`/`a`/`I`/`A`/`c`/`s`) is already live in the store on every keystroke, so ending it without capturing only loses `.`-repeat bookkeeping; a structural Insert session (`o`/`O`/whole-node-Visual `c`/`s`) is documented as cross-node repeatable by PRODUCT §20.2, so it always captures its typed text regardless of what ends it.

The shutdown flush is one shared completion path. `flushPersistence` invokes the finisher `use-node-input-bindings.ts` registers on mount, which commits a pending Replace session through the same no-DOM-rewrite path and returns to Normal mode, before it captures state for each save and again after that save completes; a replacement typed before quit is therefore part of the saved document, and a session completed while a save is in flight is saved before the flush resolves and quit confirms. A finisher reports whether it committed, so the flush takes another pass and waits for the save that commit requested instead of confirming quit with that save still in flight. A failed save leaves the committed replacement in the document for the retry. The finisher is skipped while the store is in the locked save-failure state, because a locked store rejects document changes: the session is retained until a successful final save unlocks the store or the user confirms quitting without saving.

`Cmd+.`, `Cmd+,`, and `Cmd+Backspace` previously ran `store.enter()`/`store.leave()`/`store.deleteSelected()` with no awareness of either session, silently discarding a pending Replace session's typed text (a real defect, not just a missing test) and a structural Insert session's dot-repeat capture. The node's own enter control compounds this for pointer input: its `mousedown` handler calls `preventDefault()` to avoid stealing focus while dragging, which also suppresses the browser's default blur on click, so the currently focused input never naturally loses focus before `App.tsx`'s `enterNode` runs `store.selectNode`/`store.enter()`. The fix adds an explicit pre-command finish at each of these three shortcut sites (`editor-input-handlers.ts`), and has `enterNode` blur the active element itself before navigating, so the existing blur-driven completion path finishes any pending session first. `Cmd+Z`/`Cmd+Shift+Z` already finished a pending Replace session; they now also finish a pending Insert session's bookkeeping, without forcing Normal mode, per the same "existing application commands behave normally" rule Insert already documents for other interruptions such as `Enter`.

Blur and a same-node pointer click also used to discard a pending plain or structural Insert session outright — `vimInsertSession.current = undefined` with no dot-repeat capture at all — the reverse defect from the shortcut gap above (losing bookkeeping that should have been kept, not text that should have been committed). The fix routes both through `finishVimInsert`, which now always captures a plain session's diff rather than trying to detect at finish time whether the trigger is crossing to a different node. An earlier version of this fix gated the plain-session capture on whether a blur's `event.relatedTarget` was a different tracked node's own input, but independent review found that heuristic misses real node-changing triggers that don't hand focus to another tracked input synchronously — a breadcrumb click (which focuses the clicked button, not a node input) and the node's own enter control (whose `mousedown` handler calls `preventDefault()` to avoid stealing focus while dragging, which also suppresses the browser's default blur on click, so `App.tsx`'s `enterNode` blurs the active element itself with no `relatedTarget` at all) — both wrongly captured a plain session as same-node and could later misapply it to an unrelated node via `.`. The fix instead moves the safety check to dot-repeat *replay* time: a plain session's captured change is stamped with the node ID it was captured on (`VimTextChange.nodeId`), and `.` (`vim-keyboard-handler.ts`) silently no-ops when that ID no longer matches the current node, regardless of which trigger ended the session or how it ended it. This is what the pre-existing “does not record a cross-node Insert session as a repeatable text edit” case actually protects (and now generalizes to every trigger, not only `Enter`); two new cases for the breadcrumb and enter-control mouse paths were added and confirmed to fail without the replay-time check. A structural session's capture is gated differently, at finish time rather than replay time, because PRODUCT §20.2 documents `o`/`O` as legitimately cross-node repeatable: it records the node ID it began on (`originNodeId`), because `o`/`O` immediately move focus to the newly created node as part of beginning the session, which blurs the *originating* node before any text is typed — that incidental blur must not consume the session with the wrong node's stale text; only a later blur on a node other than `originNodeId` (i.e., the new node, once the user is actually done with it) finishes it. This was found and verified by a regression in `e2e/vim-navigation-and-visual.spec.ts` (“repeats open-sibling text and rejects a subtree put into its descendant”), which failed when the fix first called `finishStructuralInsert` unconditionally from blur.

`Cmd+A`, `Cmd+V`, `Cmd+X`, the context-menu Paste/Cut, and the native paste fallback previously ran against the store text while a pending Replace session still held its pre-command baseline, so the store changed under the session and the commit that followed applied pre-command offsets: `abcd` at cursor 2, `R`, `X`, `Cmd+V` of `PASTED`, `Y`, `Escape` produced `abXYASTEDd`. The same commands left a character Visual endpoint pair describing the pre-command text, so the next motion re-anchored nowhere near the pasted text. A real-renderer probe also found that `Cmd+A` during Replace triggered a controlled-textarea render that rewound the visible typed replacement to the stored text (`abXd` became `abcd`) before the command could act. One rule now resolves the session before these commands (`finishVimSessionBeforeTextEdit` in `editor-input-handlers.ts`): a pending Replace edit commits as one edit and returns to Normal without rewriting the DOM — the visible text already equals the committed text — so a following select-all, cut, or paste acts on the user's selection, and `Cmd+A` uses the same preserving commit before selecting all. A right-click context menu gets the preserving commit in `onMouseDown` for `button === 2`, so the menu still sees the selection. Otherwise the unfinished command and both character endpoints clear while character Visual mode stays active; Insert sessions and whole-node Visual mode and its range are untouched, and a `Cmd+X` with no selection stays a no-op that does not consume the session.

The following matrix combinations are intentionally inapplicable under the specified behavior: `h` does not enter an image from text; `l` does not leave an image for another node; an image-only node has no text position to restore; and text operators/character Visual selection do not extend across the image or into another node. No broader Vim compatibility is inferred from the command names.

The bounded mixed-sequence guard in `src/renderer/vim-mixed-interaction.property.test.ts` compares the production keyboard handler and `EditorStore` with an independent expected-state model after each generated event. Its fixed seed covers counted motions and replacements, empty and image-only roots, cross-node and boundary motion, pointer focus, count interruption, text deletion, and undo/redo including edit-after-undo. A preserved seed (`711207`, path `20`) found that standalone text replacements recorded duplicate history snapshots: two separate `r` edits required an empty undo step between them. The named deterministic regression and a real-Electron case assert one undo per edit; `src/application/editor-store.test.ts` also guards 120 standalone edits near the history limit. The fast generated suite uses 80 runs of at most 22 events over at most four short nodes. Its generated history events never arrive with a command pending, because every generated event assembles and consumes its own count and the model asserts an empty pending slot after each step; that is why `Ctrl+r` redoing after an unfinished command went unnoticed, and why the unfinished-command rows above carry focused and Electron evidence instead.
