# Vim conformance matrix

This is a test inventory for the behavior specified in [PRODUCT.md](PRODUCT.md) §4.3 and §20.2. It does not define additional Vim behavior. “Covered” means that the named automated tests exercise the stated case; it does not claim that every possible key sequence is tested. The navigation dimensions follow [DEVELOPMENT.md](DEVELOPMENT.md) §8.

## Interaction-state contract

This contract makes the existing [PRODUCT.md](PRODUCT.md) §20.2 behavior and its focus/caret test expectations explicit. It does not add commands or change state ownership. A transition's observable state is the selected node, Vim mode, focused input, text selection or image caret, and (when an image was entered from text) the text position to restore. The store's focus intent has a node ID, cursor, and monotonically new token; the token distinguishes an intentional focus request from an unchanged store focus after a local caret motion. The selected node ID alone cannot make that distinction.

| State or event | Contract |
| --- | --- |
| Normal text and image caret | Exactly one caret is active on the selected node. Text positions are character indices, with a block selection on the current text character. An attached image is the terminal character at `text.length`; on an image-only node, index `0` is the image and there is no text position to save. |
| Saved image return position | Same-node `j` from text and `l` from text into the image save a valid position in that node's text. `k` or `h` from the image restores it, with a remaining count applied for `h`. An in-node move to text, edit that lands on text, or cross-node move clears it. It never belongs to another node. |
| Focus intent | A successful store navigation, history operation, structural operation, or explicit selection supplies a fresh focus token, including when the selected node ID remains the same. The renderer applies its target cursor to focus and derives the image caret from the target node and cursor, superseding an older saved return. Local character motion changes the caret without a store focus request; an unchanged token must not replay an older focus cursor over it. |
| No-op and clamped transition | An unavailable undo, redo, or leave and whole-node Visual entry followed by exit without movement produce no new focus intent, so the active image caret and saved return position survive. A failed in-node search leaves the caret in place. A level-boundary motion can explicitly reselect the same node with a new focus cursor; it must apply that cursor even though the node ID is unchanged. Clamped `k` on an image-only first root retains its image caret, while a whole-node Visual clamped move selects cursor `0` and clears a prior text-plus-image caret. |
| Modes and pointer input | Normal uses the text block or image caret; Insert and Replace use the thin text caret; character Visual and whole-node Visual own their selections. Escape and Visual exits resume Normal at the documented cursor. Pointer focus/selection preserves the current Vim mode and places the text caret at the pointer-selected position; leaving an image through pointer input drops the old saved return. A pending Replace edit is committed before an application history, node-entry, node-leave, or node-delete command runs, whether triggered by keyboard or a pointer click (including the node's own enter control, whose `mousedown` handler otherwise suppresses the browser's default blur). |

The store owns location and focus intent; the renderer owns mode, DOM caret/selection, image-caret indicator, and saved image return position. This is a characterization of the current architecture for the VIM-2 tests, not an implementation of the later transition model. Focused coverage for token-sensitive no-ops and same-node requests is in `src/application/editor-store.test.ts` and `src/renderer/use-node-input-bindings.test.tsx`; the rows below map representative Electron behavior.

The navigation gaps closed earlier were the image-only horizontal/boundary and two-way vertical transitions, a counted move that crosses an image row before changing siblings, and pointer exit from an image state. The edit-to-caret rows above cover the subsequently found mutation gaps. History and current-parent boundary commands (`u`, `Ctrl+r`, `Ctrl+o`) closed a later-found gap, entering a childless attachment-bearing node (`gd`, `Cmd+.`, its enter control, or an ancestor breadcrumb click) closed the next gap, and whole-node Visual mode's own moves and mutation commands closed another gap: each changed focus without resyncing the image-caret indicator. The remaining no-op path gap was caused by resynchronizing from an old store focus intent after local image motion; only a new focus token now supersedes that local caret. Search, named registers, macros, and marks are explicitly unsupported by PRODUCT §20.2 and have no conformance rows.

Edit-result, Visual-leave, Replace-commit, and Insert-Escape caret updates now share one pure transition function (`editCaretTransition` in `src/renderer/vim-caret-transition.ts`) instead of recomputing the clamp-plus-image-active rule ad hoc at each call site. That refactor found one previously untested gap: a pending Replace session committed on blur always cleared the image caret regardless of where the committed text ended, because the caller-side Escape/undo/redo retreat-by-one adjustment and the image-caret decision were computed independently. The fix makes the image-caret decision use the same final caret position each caller actually leaves behind: `finishReplace`/`finishVimReplace` takes an explicit `retreatCursor` flag rather than inferring it from whether a DOM element was passed, since a same-node pointer click also passes one but, like blur, never retreats the caret afterward — only Escape, `Cmd+Z`, and `Cmd+Shift+Z` do. Node entry/exit while the selected node ID stays the same (`gd`, `Cmd+.`/`Cmd+,`, the enter control, breadcrumb navigation, whole-node Visual moves and mutations) and undo/redo were already fully routed through `focusCaretTransition` via `syncImageCaretToFocus` as of the vertical/count-navigation work; re-verifying their existing coverage found no further gap.

## Insert and Replace completion policy

Insert and Replace sessions are mutually exclusive at any instant: Replace only starts from Normal mode with `R`, and unmodified keys never reach Vim command handling while Insert mode is active. Their completion needs differ by what they hold: Replace buffers typed text only in a ref and the DOM, so ending it without committing is data loss; a plain Insert session (`i`/`a`/`I`/`A`/`c`/`s`) is already live in the store on every keystroke, so ending it without capturing only loses `.`-repeat bookkeeping; a structural Insert session (`o`/`O`/whole-node-Visual `c`/`s`) is documented as cross-node repeatable by PRODUCT §20.2, so it always captures its typed text regardless of what ends it.

`Cmd+.`, `Cmd+,`, and `Cmd+Backspace` previously ran `store.enter()`/`store.leave()`/`store.deleteSelected()` with no awareness of either session, silently discarding a pending Replace session's typed text (a real defect, not just a missing test) and a structural Insert session's dot-repeat capture. The node's own enter control compounds this for pointer input: its `mousedown` handler calls `preventDefault()` to avoid stealing focus while dragging, which also suppresses the browser's default blur on click, so the currently focused input never naturally loses focus before `App.tsx`'s `enterNode` runs `store.selectNode`/`store.enter()`. The fix adds an explicit pre-command finish at each of these three shortcut sites (`editor-input-handlers.ts`), and has `enterNode` blur the active element itself before navigating, so the existing blur-driven completion path finishes any pending session first. `Cmd+Z`/`Cmd+Shift+Z` already finished a pending Replace session; they now also finish a pending Insert session's bookkeeping, without forcing Normal mode, per the same "existing application commands behave normally" rule Insert already documents for other interruptions such as `Enter`.

Blur and a same-node pointer click also used to discard a pending plain or structural Insert session outright — `vimInsertSession.current = undefined` with no dot-repeat capture at all — the reverse defect from the shortcut gap above (losing bookkeeping that should have been kept, not text that should have been committed). The fix routes both through `finishVimInsert`, which now always captures a plain session's diff rather than trying to detect at finish time whether the trigger is crossing to a different node. An earlier version of this fix gated the plain-session capture on whether a blur's `event.relatedTarget` was a different tracked node's own input, but independent review found that heuristic misses real node-changing triggers that don't hand focus to another tracked input synchronously — a breadcrumb click (which focuses the clicked button, not a node input) and the node's own enter control (whose `mousedown` handler calls `preventDefault()` to avoid stealing focus while dragging, which also suppresses the browser's default blur on click, so `App.tsx`'s `enterNode` blurs the active element itself with no `relatedTarget` at all) — both wrongly captured a plain session as same-node and could later misapply it to an unrelated node via `.`. The fix instead moves the safety check to dot-repeat *replay* time: a plain session's captured change is stamped with the node ID it was captured on (`VimTextChange.nodeId`), and `.` (`vim-keyboard-handler.ts`) silently no-ops when that ID no longer matches the current node, regardless of which trigger ended the session or how it ended it. This is what the pre-existing “does not record a cross-node Insert session as a repeatable text edit” case actually protects (and now generalizes to every trigger, not only `Enter`); two new cases for the breadcrumb and enter-control mouse paths were added and confirmed to fail without the replay-time check. A structural session's capture is gated differently, at finish time rather than replay time, because PRODUCT §20.2 documents `o`/`O` as legitimately cross-node repeatable: it records the node ID it began on (`originNodeId`), because `o`/`O` immediately move focus to the newly created node as part of beginning the session, which blurs the *originating* node before any text is typed — that incidental blur must not consume the session with the wrong node's stale text; only a later blur on a node other than `originNodeId` (i.e., the new node, once the user is actually done with it) finishes it. This was found and verified by a regression in `e2e/vim-editing.spec.ts` (“repeats open-sibling text and rejects a subtree put into its descendant”), which failed when the fix first called `finishStructuralInsert` unconditionally from blur.

The following matrix combinations are intentionally inapplicable under the specified behavior: `h` does not enter an image from text; `l` does not leave an image for another node; an image-only node has no text position to restore; and text operators/character Visual selection do not extend across the image or into another node. No broader Vim compatibility is inferred from the command names.

The bounded mixed-sequence guard in `src/renderer/vim-mixed-interaction.property.test.ts` compares the production keyboard handler and `EditorStore` with an independent expected-state model after each generated event. Its fixed seed covers counted motions and replacements, empty and image-only roots, cross-node and boundary motion, pointer focus, count interruption, text deletion, and undo/redo including edit-after-undo. A preserved seed (`711207`, path `20`) found that standalone text replacements recorded duplicate history snapshots: two separate `r` edits required an empty undo step between them. The named deterministic regression and a real-Electron case assert one undo per edit; `src/application/editor-store.test.ts` also guards 120 standalone edits near the history limit. The fast generated suite uses 80 runs of at most 22 events over at most four short nodes.
