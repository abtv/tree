# Desktop Notes Replacement and Archive

### 13.12 Desktop notes replacement

#### 13.12.1 Commit and Journal

Desktop import replaces the notes as one crash-safe unit ([ADR 0024](../decisions/0024-desktop-notes-archive.md)). `src/infrastructure/main/notes-replacement.ts` owns the layout beside `data/` (`.notes-import/`, `.notes-export/`, `Replaced Notes/`), the commit and the roll-forward recovery, through a file-system port that tests use for fault injection. The commit writes its journal as `commit.json.tmp`, flushes and renames it, so the journal is either absent or complete; before that rename a failure leaves the notes unchanged, and after it only completion is possible. Each step checks what remains: while the staged `document.json` exists, every document file in `data/` is old, and `data/attachments` is old while the staged `attachments/` exists, so staging always contains that directory. A replaced-notes folder that already exists means an interrupted run moved part of the previous notes there. An empty previous `attachments/` without document files creates no folder. The commit flushes the staging directories before the journal, creates `data/` when a new profile has none, and flushes `data/` and staging before the staged document moves, because that document's presence in staging is the marker of unfinished work and every earlier move must be durable before it disappears.

#### 13.12.2 File-Service Integration

`src/infrastructure/main/file-services.ts` runs recovery inside `load`, before it selects the newest valid candidate, and sweeps staging and export snapshots that no running operation registered. A recovery failure fails the load with `The notes import could not be completed: <reason>` and opens nothing, so a damaged imported document can never fall back to a replaced generation. `replaceNotes` runs the commit as one queued operation. From the journal on, saves and attachment writes reject and cleanup does nothing until the next load, so the replaced session cannot write its document over the imported one; the cached generation number resets. `snapshotDocuments` hard-links the current document files into a new export directory inside the queue: saves only rename those files, so the links keep the exact bytes and times that `findNewestValidDocument` selects from. A leftover `document.json.tmp` is copied with its times instead, because the next save rewrites it in place. `pinAttachments` adds IDs to every cleanup keep set until released.

Performance assessment (PRODUCT.md §22.1): a load without a journal adds one journal read and one listing of each of the two small directories; editing and saving add one flag check. A commit is a constant number of renames and directory flushes plus one rename per document file (at most the generation cap plus three); images move as one directory rename, so no image bytes are read, written or flushed. A snapshot is at most that many hard links. No operation retains memory proportional to the notes.

#### 13.12.3 Roll-Forward Recovery

Recovery validates the journal before mutating files. A valid journal authorizes resumable roll-forward: a later filesystem failure can leave completed moves in place. Loading remains blocked, and the journal and remaining staging are retained until the replacement steps complete. This is logical replacement atomicity for readers, not a promise of zero filesystem changes on a failed recovery (PRODUCT.md §25.4). Fault-injection tests cover interruption of both the initial commit and subsequent recovery; deterministic recovery coverage interrupts every filesystem-operation boundary and retries after repeated failures.

### 13.13 Desktop notes archive

#### 13.13.1 Archive Worker and Jobs

Desktop export and import ([ADR 0024](../decisions/0024-desktop-notes-archive.md)) run in a Node `worker_threads` worker that the main process starts per operation. `src/infrastructure/main/notes-archive/` holds the message protocol, the worker entry and its two jobs; `config/build/electron.vite.config.ts` builds the entry as `out/main/notes-archive-worker.js`. The worker belongs to the main process, so it needs no exception to the renderer's `worker-src 'none'` policy. The jobs reuse the browser's archive code: `desktop-export-job.ts` selects the newest valid document in an export snapshot with `findNewestValidDocument`, asks the main process to pin its image IDs before reading any image from `data/attachments`, and writes the archive with the shared writer to a hidden, exclusively created sibling of the destination, which it opens with the first entry and flushes at the end. `desktop-import-job.ts` reads the chosen file at positions, runs `prepareNotesImport` against the import's empty staging directory, checks each image's structure itself and asks the main process to decode it, writes each image and then `document.json` with flushed writes, and counts the current notes from a snapshot that the main process takes after staging. Each request waits for one reply, so the worker never has two outstanding.

#### 13.13.2 Main-Process Controller

`src/electron/main/notes-archive-controller.ts` owns the native panels, which open as sheets, and runs one operation at a time. The renderer's requests carry no arguments; it receives file names, counts, progress and the Replaced Notes folder as display text with the home directory shown as `~`, never a path it could send back. After the worker reports a complete export, the controller renames the hidden file to the destination and flushes the directory, so the destination changes only when the archive is complete; a directory flush that the volume refuses after the rename does not fail the export. The jobs open files as `FileHandle`s, which Node closes itself when they are left open, as a terminated worker leaves them; a bare descriptor would stay open until the application quits. Cancelling terminates the worker, waits until its thread has stopped and no request is being answered, then removes the hidden file or staging directory, releases the snapshot and unpins the images. A commit calls `replaceNotes` with the archive name, which the journal records for a recovered replacement's notice. A failure before the journal discards staging and leaves the session usable; a failure after it marks the session as needing a restart, and the controller refuses further operations. Show in Finder reveals only a folder that a commit or a recovery reported. On quit, `bootstrap.ts` asks `settleBeforeQuit` once the renderer has confirmed: export and preparation are cancelled with their cleanup, and a running commit is awaited, before the application quits again.

#### 13.13.3 Renderer Write Suspension

In the renderer, `src/infrastructure/renderer/electron-services.ts` suspends saves, image writes and attachment cleanup while a replacement runs; they resolve without reaching the main process, and a rejection with `NOTES_REPLACED_MESSAGE` suspends them as well, so the replaced session shows no save error before its window reloads.

#### 13.13.4 Desktop Data Coordinator

`DesktopDataOperations` in the application archive layer coordinates the desktop export flow behind a `DesktopNotesApi` port. The native File menu sends an export command; the coordinator chooses the destination, flushes pending edits through `EditorStore.flushPersistence`, and starts the archive operation. Its operation epoch ignores late responses after cancellation or disposal. It keeps one result-expiry timer, removes its subscriptions on disposal, and waits for cancellation cleanup before accepting another export. The renderer entry constructs it only for desktop. `DataActivityPanel` presents its state without subscribing the editor to progress updates and restores focus when a focused panel closes.

Import notices request initial focus on the result action, so OK and Show in Finder are keyboard reachable without entering the node editor's structural Tab handler. The panel captures the preceding editor/control before focusing OK and does not repeat that focus on text updates. Confirmation focuses Cancel whenever it returns to its interactive state after export. Button outlines depend on actual focus rather than the most recent input device, following PRODUCT.md §20.7. These focus transitions cost constant DOM work and cause no persistence writes or document-scale state.

Menu availability crosses a validated boolean-only IPC channel; the coordinator sends it only when the enabled states change. Main resets availability and cancels archive work when the main frame navigates or its renderer exits, including prepared imports awaiting confirmation. Import stays available after a load error. Performance assessment (PRODUCT.md §22.1): the coordinator retains no document, adds constant work to each store notification, and holds only the current activity, subscriptions and timer. Progress adds a bounded panel update, with no tree traversal. The explicit export flush performs only the writes and syncs of `flushPersistence` (§13.8.3); menus and progress add none. The archive performance guard covers large-document typing with this subscription installed.

The coordinator also owns import preparation, confirmation, replacement and the one-shot result after loading. `ImportConfirmationDialog` presents its counts and messages, traps focus with the native HTML modal mechanism, and restores focus on dismissal. Export Current Notes First runs inside that modal: main retains the prepared import while its export worker runs, restores it when the export ends or its save panel is cancelled, and discards both operations on cancellation, navigation or quit. `notes-archive-controller.ts` carries that import as `suspended` inside its choosing, export-chosen and running states, and refuses another import choice while one is suspended, so a second preparation cannot orphan the first staging directory. Replace flushes pending edits before suspending renderer writes, then reloads on success. A pre-journal failure resumes writes; a post-journal failure or an uncertain commit IPC outcome keeps the modal blocked and writes suspended until restart. The result panel displays the main-provided folder text and invokes argument-free Show in Finder. Import presentation retains only counts and short text, with no document-scale CPU work and no persistence beyond the flush, staging and replacement operations.

Its lifecycle, current operation and prepared-import state are independent regions. Choosing and running operations own their import/export direction; running also distinguishes flushing from transfer. `DataActivity` is a cached UI projection, so internal stage changes do not add notifications or replace an unchanged public snapshot. A replacement owns one attempt record, retained locally across awaits, whose `flushing` or `committing` stage determines whether failure is ambiguous. Preparation survives exports from confirmation and follows the cleanup lifetime independently of progress or disposal. These records are bounded and cause no writes, syncs or document-scale work of their own.

#### 13.13.5 Costs and Guards

Performance assessment (PRODUCT.md §22.1): starting an operation adds a worker start, at most the generation cap plus three hard links and one directory listing per snapshot. The main thread does constant work per worker message, except one platform PNG decode per imported image. Export writes the archive once with one flush and one rename; import writes each referenced image and the document once with one flush each, then commits as above. The worker holds the document, one image and the archive's central directory; the main process and the renderer hold no document or image bytes beyond the image being decoded. Editing adds one flag check per save, image write and cleanup.

`perf/electron/notes-archive.spec.ts` compares visible typing at idle, during export and during import preparation on a large synthetic profile with referenced PNGs, including images near the attachment byte limit. It records key-to-frame latency, operation duration, main event-loop delay and sampled main JavaScript heap growth, and checks that cancelling active preparation closes the worker's archive file and removes staging. The local measurement kept per-image main-thread work within the guard, so the native decoder remains in the main process under ADR 0024. The heap measurement excludes native image memory and worker heaps; timer samples can miss short heap peaks.
