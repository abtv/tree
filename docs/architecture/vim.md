# Vim Editing

### 8.3 Vim Pointer Continuation and Vertical Navigation

#### 8.3.1 Replace Pointer Continuation

The `vim-edit-session.ts` owner represents Replace pointer continuation as idle, pressed or settling, with one press identity, destination and focus-movement flag. Deferred release settlement consumes only that identity; native mouseup or a first replacement key can consume it synchronously. The hook keeps general native pointer-held selection separate, bounds pending settlement to one timer, and cancels it on cleanup. These state models have no persisted fields and cause no document writes, syncs, history entries or per-motion subscriptions of their own. Their transitions are constant-time apart from the text/geometry and projection work.

#### 8.3.2 Vertical Navigation

Tree Normal vertical navigation uses `vim-vertical-navigation.ts` for caret and node transitions and a text-line callback measured by `editor-dom.ts`. Rich inputs use DOM ranges; textareas use a temporary mirror with the current computed font and width. An unmounted destination uses a temporary hidden row under the real list, sharing its indentation and input styles. Measurements live only for the command and are disposed afterward. `VimCommandState.verticalGoal` retains one desired horizontal position with the expected node, cursor, focus token, text and viewport width; mismatching context or a nonvertical command invalidates it. Pointer input clears it through the command-state owner; a blur caused by vertical navigation preserves it for the destination.

Agenda Normal vertical commands reuse `visualTextGeometry` and `visualLineCursor` through `agenda-text-geometry.ts`. The adapter resolves occurrence keys, measures the mounted editor/label, and uses an Agenda-styled hidden row for an unmounted destination. The shared vertical goal includes its Agenda occurrence key, so repeated nodes in different days do not share stale geometry. Same-node steps use the caret projection or the synthetic row's local caret, without publishing document state. Cross-row selection marks the focus intent for line reveal; vertical blur preserves the goal across editor and synthetic-row focus. Counts include visual lines rather than being capped by the number of projected rows. A command keeps only the current row's measurement and disposes it before measuring another row, so large counts do not accumulate hidden DOM rows. Final disposal releases the remaining measurement; Agenda vertical commands cause no document writes or history state of their own.

After the final Normal vertical step, the input bindings request a text-line reveal from `viewport-reveal.ts`. Its single intent resolves the currently registered input, measures the caret line through `editor-dom.ts`, and applies the shared viewport-context policy. Single-line Agenda entries use their complete minimum-height row bounds, matching heading and separator reveals; wrapped or attachment rows use the caret-line bounds. That choice costs one bounded row geometry/style read and keeps no state. The text-line reveal waits for an unmounted destination and replaces whole-row focus reveal for this motion. The caret owner's revision, mode and store focus token invalidate stale corrections. Resize and layout corrections remeasure the line; deliberate scrolling cancels the intent. The reveal uses one bounded destination record and text measurement per correction, with no document traversal or direct disk writes; changed scroll positions use the coalesced viewport persistence.

Performance assessment (PRODUCT.md §22.1): vertical motions perform layout reads over the visited inputs, with binary searches for line boundaries and a nearest-character scan of the destination line that also handles bidirectional text. They retain at most the command's measured rows until disposal plus one desired-position record afterward. They cause no document edits or history entries and perform no direct disk writes or syncs; a Tree step that changes the selected node marks a persisted change for the idle autosave (§21.1.5). The windowed Normal-navigation performance scenarios guard document-scale latency; wrapped-line E2E cases guard layout and cleanup behavior.

#### 8.3.3 Pointer Selections in Normal and Visual Mode

`use-node-input-bindings.ts` records the node editor under a held primary press in `heldTextPress`, with whether the press is ordinary (a mouse press without `Cmd`, `Ctrl` or `Option`), whether it extends with `Shift`, and, for a text area, the offset under the press from `textAreaOffsetAtPoint`, read before the native press moves the caret. Until release the native press owns that editor's selection. The Normal block caret is a one-character native selection; Chromium keeps a press that lands on a drawn range as the drag's anchor. Every Normal block write to the pressed editor (the focus projection, `applyCaretState`, a compatible pending placement and the mode projection) therefore skips it, and the release redraws the block. `NodeInput` re-applies a retained selection after a render only when it differs from the live one, because an unchanged rewrite also resets a drag in progress. An ordinary press also collapses a character Visual or `Cmd+A` range first, as it collapses the block, so it starts a new selection. Chromium would otherwise treat the press as a native text drag and collapse the range only after the `pointerup` that settles the mode, which would then read the old range. A `contextmenu` and the effect cleanup clear the record, because a native menu can swallow the release. The listeners keep the `pointerId` and type of the held press: another pointer's press or release, such as a finger lifted from a touch screen during a mouse drag, leaves it alone, including its Replace click settlement. A mouse press, or a new primary pointer of the held type, takes over, because it proves that the earlier press ended even when its release was lost. Only a mouse press is ordinary; touch and pen keep the mode.

The window `pointerup` listener settles an ordinary press released on the editor that still has focus, in Normal or character Visual mode. `getPointerSelectionEndpoints` in `editor-dom.ts` reads the native endpoints within the pressed editor. A browser rich field is not editable in Normal and Visual mode, so a drag can leave it; an end outside it is clamped to its nearer edge, and `isSelectionWithin` tells the settle step to write that clamped range back, so the commands read the range Visual shows. A macOS text area reports no direction, so a release before the pressed offset selects backward and any other release forward, which keeps a multi-click without movement forward, while a `Shift` press takes its focus from the end under the released pointer. The release point is first moved to the nearest point inside the text area, because Chromium's `caretPositionFromPoint` beside it reports offset zero. `pointerSelectionTransition` in `vim-caret-transition.ts` turns those boundaries into inclusive Visual endpoints, written with the `gv` memory by `setVisualRange`, or into Normal mode (PRODUCT.md §20.2.6). A node drag blurs the pressed editor first, so its release changes no mode.

The press record is one bounded object. A text area press performs one hit test, and a release one selection read and at most one hit test, with no document traversal, edits, history entries, disk writes or syncs. Focused rule tests cover the transition, the endpoint read and the skipped writes; `e2e/electron/vim-navigation-and-visual.spec.ts` and `e2e/electron/agenda-vim.spec.ts` cover real pointer dispatch in plain and rich editors, and `e2e/web/pointer-visual.spec.mts` covers a drag that leaves a browser rich field.

### 21.1 Vim and Caret Owners

#### 21.1.1 Renderer Module Map

The renderer isolates DOM/caret behavior in `editor-dom.ts`, the Normal-mode caret target and pending hyperlink-draft currency in `link-caret.ts`, pure Vim motion and text-object calculations in `vim-editing.ts` and `vim-text-commands.ts`, surround delimiter and edit calculations in `vim-surround.ts`, the Vim register and Insert/Replace session owner plus session-completion helpers in `vim-edit-session.ts`, the Vim command-state owner in `vim-command-state.ts`, Vim command dispatch in `vim-keyboard-handler.ts`, keyboard state types in `vim-keyboard-types.ts`, and standard shortcuts and context-menu routing in `editor-input-handlers.ts`. Location rendering lives in `LocationBar.tsx`, attachment rendering/preview in `AttachmentPreview.tsx`, list geometry and measurement in `node-list-layout.ts`, row presentation in `NodeRow.tsx`, and drag interaction in `use-node-list-drag.ts` with the pure gate fold in `node-drag.ts` and the pure caret-freeze record in `drag-caret-freeze.ts`.

The input bindings hook `use-node-input-bindings.ts` keeps every owner instance, ref, and effect and builds each handler group from an extracted module that receives them as explicit arguments and keeps no module-level state: `node-input-types.ts` (pending caret and Visual selection types), `caret-projection-rules.ts` (the pure currency rules for pending caret work), `vim-viewport-motion.ts` (H, M, L, and half-page targets), `vim-structural-repeat.ts` (dot replay of structural changes), `vim-node-visual-commands.ts` (whole-node Visual and sibling-range commands), `vim-session-finish.ts` (Insert, Replace, and structural session finishing and the Vim editing switch), `vim-keyboard-state.ts` (the `VimKeyboardState` adapter), `node-input-text-handlers.ts` (text edit, link draft, and composition handlers), and `node-input-pointer-handlers.ts` (blur, focus, pointer, select, paste, cut, link click, and context menu).

The hook holds one `vim-edit-session.ts` owner, one `vim-command-state.ts` owner, and one `caret-projection-state.ts` owner for renderer-local mode and caret state, including the image return position. It also holds the drag caret-freeze record. It reconciles the image-caret indicator with a new store focus token; a command that produces no new focus intent leaves the local caret and saved return position intact. An explicit image destination consumes the new token so a later render does not replace it with the store's text boundary.

The whole-node Visual selection stores only two displayed sibling IDs in `App.tsx`, and `NodeList.tsx` renders highlighting by comparing their indices with mounted rows, including pinned focused rows in a windowed list. The selected subtree range is derived from the document when a command executes; selection is not persisted.

The renderer modules listed in this subsection are UI adapters and dispatch completed document changes through the application layer.

#### 21.1.2 Caret Authority and Projection

`caret-projection-state.ts` is the pure renderer-local owner for caret authority, pending caret and Visual placement, mode and focus currency, and the consumed image-focus token. The hook holds one instance rather than separate refs for those facts. Command, completion, pointer and drag adapters call its transitions. One layout-effect pipeline synchronizes authority, projects a changed mode, applies a changed focus and viewport policy, restores Visual endpoints, applies current pending placement, refreshes selection decoration, and reconciles completion, in that explicit order. Commit gates preserve native selection on unrelated renders. Deferred focus work captures the owner's focus token and revision; a later placement, mode change or restored selection invalidates it. DOM input currency and textarea-to-rich replacement live in `caret-projection-rules.ts`. Replacing a focused textarea retains its directional selection through that same pending-placement owner, using the previous committed focus token. This fallback yields to explicit caret or Visual work and newer focus intents; `NodeInput` never independently restores focus. This design follows ADR [0014](../decisions/0014-single-owner-for-renderer-interaction-state.md), causes no disk operations or document traversal of its own, and retains one bounded request per placement kind rather than a queue.

The renderer computes Normal-mode caret state through pure renderer-local transitions in `vim-caret-transition.ts`: horizontal and vertical motion, counted cross-node navigation, focus intents, pointer focus, and no-op boundaries, together with text-edit and Visual-leave results, Replace commits, and Insert Escape (`editCaretTransition`), plus node entry/exit and undo/redo focus changes (`focusCaretTransition`). `use-node-input-bindings.ts` retains one caret authority for the caret, the active image, and the saved return position and projects the image state to React; the DOM caret class renders that result. It also owns the drag caret freeze: a drag can only ask the authority to suspend or release the caret, and the pure capture record lives in `drag-caret-freeze.ts`. Release schedules the captured state through the pending-caret owner, bound to the move's focus token. Projection restores it on the currently registered input after focus processing and invalidates the move's deferred caret pass. A newer focus intent, caret revision or drag supersedes that request. Outside-list drop dispatch runs in window capture before the caret owner's bubble release listener, so toolbar moves publish their focus intent before restoration is scheduled. The freeze retains one bounded request; its release and projection are constant-time work and cause no document traversal, disk writes or syncs of their own. `vim-keyboard-handler.ts`, `editor-input-handlers.ts`, and the input bindings adapt pure results to DOM placement and store navigation.

Each caret transition performs constant-time arithmetic and retains only a cursor and optional return position. Counted navigation invokes one transition per motion step. A caret transition causes no disk writes or syncs of its own, does no work that scales with document size or edit count, and keeps no growing history. The bounded property tests exercise counted motion and return-position invariants across varied text lengths and node layouts, and a bounded mixed-sequence guard compares the production Vim keyboard handler and `EditorStore` with an independent expected-state model over generated interaction sequences.

#### 21.1.3 Edit Session and Command State Owners

`vim-edit-session.ts` owns the renderer-local Vim register and the one pending Insert or Replace session, together with the pure diff and Replace-commit helpers. `vim-command-state.ts` owns the pending command, the last repeatable change, the last character find, the character-wise Visual endpoints, the latest Visual selection remembered for `gv` (a character range as node and offsets, a whole-node range as its endpoint IDs and the ascending sibling IDs between them; it is renderer-session only, survives every clear, and is written together with the live endpoints by one transition), and the one structural Insert session; `vim-visual-memory.ts` holds the pure rule that decides whether that memory is still valid and displayed. `use-node-input-bindings.ts` holds one instance of each owner and projects their results into React, the DOM, and the store; it performs its command-state writes through that module's transitions, and the keyboard state carries the command-state owner so `vim-keyboard-handler.ts` and `editor-input-handlers.ts` read and write the same object and clear the pending command and Visual endpoints only through its transitions. It finishes a pending session through one shared policy (`vim-session-finish.ts`) for Escape, blur, application shortcuts, undo/redo, and the shutdown flush. Plain and structural Insert sessions record for `.` only when Escape completes them; interruptions consume their bookkeeping and retain the previous repeatable change (PRODUCT.md §20.2.19). A structural session records its origin node so the incidental blur that begins its new node does not end it. Replace pointer continuation uses the idle/pressed/settling gesture state described in §8.3.1, not a separate boolean. These session transitions cause no disk writes or document traversal of their own and retain only the current bounded session and repeat payload.

Standard (non-Vim) editing is the Vim layer switched off, not a second editor. `App.tsx` owns the enabled flag; while it is off the renderer Vim mode stays `insert` and `use-node-input-bindings.ts` passes no Vim keyboard state to `createEditorKeyDownHandler`, whose standard command branch then handles every key, so Normal-only paths (image caret, block caret, Normal pointer handling) stay inert and no Vim session can begin. The hook's `setVimEditing` performs the switch on the focused input through the same session-finishing policy as a focus change — Insert bookkeeping, a Replace commit that does not rewrite the DOM, cleared command assembly and whole-node Visual range — but keeps focus; switching on lands in Normal mode with the caret projected through `editCaretTransition`.

#### 21.1.4 Command Interruption, Counts and Pending Commands

`vim-session-finish.ts` also owns command interruption policy. App, keyboard and pointer adapters name the interruption or supply observed focus/pointer facts; the module selects the Insert/Replace completion, selection preservation, command clearing and mode transitions. Search open and jump, text editing, navigation, view changes and history are distinct policies. `VimTextCommandState` provides live owner-backed handles without coupling search and pointer callers to the keyboard handler. Blur preserves a structural session started from the departing node and a verified vertical arrival goal. Replace-click continuation updates the edit-session owner through its transition. Escape, toggle and flush use their completion paths; the policy keeps no parallel state.

`vim-command-state.ts` owns shared count accumulation and character-command assembly for editable text and Agenda rows. It consumes an awaited character before command classification, records character finds, retains operator counts, and leaves execution to each adapter. The two count policies preserve Agenda's different zero/prefix handling. Prefix dispatch, row-count limits, readonly replacement, structural commands and surround stages remain with their specialized adapters; this is not a shared Vim executor.

`VimPendingCommand` is a local union of count, operator, prefix, awaited-character and surround variants. Required payload fields discriminate the variants; an absent pending command is idle. Prefix and character variants can carry an operator, while surround stages exclude operators, prefixes and awaited characters. Handlers construct complete variants instead of mutating an optional field into another variant. Character assembly refuses an unresolved prefix or surround stage; the adapters dispatch those stages before character assembly.

These coordination transitions cause no document traversal, subscriptions, disk writes or syncs of their own. They retain only the pending command and session. Count input is proportional to its digit string; no history of commands is retained.

#### 21.1.5 Cross-Node Motion

Cross-node motion (`↑`, `↓`, `j`, `k`, `←`, `→`, `G`, and their counted forms) is resolved by `moveSelectionTransition`, `moveHorizontalTransition`, and `moveSelectionBoundaryTransition` in `editor-command-transitions.ts` against the visible-row list `EditorStore.getVisibleRows()` returns, locating the current row with one linear scan of that list. `vim-vertical-navigation.ts` issues one such call per step of a counted vertical motion, so an `N`-step motion costs `O(N)` scans of the current location's visible rows. Every step of one counted motion reuses the same memoized row array, because a motion step changes only the selected node, not the document, current parent, or expansion identity that the memoization key uses. The underlying `O(visible rows)` traversal rebuilds that array only when one of those cache inputs changes, not on every render.

Performance assessment (PRODUCT.md §22.1): cross-node motion performs no direct disk writes or syncs; each step that changes the selected node marks a persisted change, which the idle autosave coalesces. CPU per motion step is bounded by the visible rows of the current location, not the whole document, so a counted motion costs `O(count × visible rows)` in the worst case; navigation reads the memoized row array rather than allocating one per step. `perf/electron/expansion.spec.ts` guards this path at 1,100 visible rows for both single-step and counted vertical motion.

#### 21.1.6 Register and Text Mutations

Vim text mutations use the same application-layer edit and history path as ordinary text edits. The local Vim register is renderer-local and holds either one node-sized string, one immutable subtree snapshot, or one ordered forest snapshot; structured puts go through an application transition that remaps every node ID and updates attachment reachability. The register is neither persisted nor sent across IPC. Motions and range edits scan only the active node text; subtree puts additionally scale with the copied subtree. Repeat state retains one command descriptor and, for Insert and Replace changes, only the most recent replacement text. The last character-find and active Replace baseline are each bounded by one current-node value. Counts stop at text boundaries; counted text puts allocate the requested output once, and counted dot changes scale with the requested repetitions. These commands perform no direct disk operations; their writes are those of the autosave path. They do not accumulate state across edits.

#### 21.1.7 Whole-Node Visual Commands and Clipboard Export

Whole-node Visual commands dispatch through `EditorStore` and replace a sibling interval in one immutable domain operation and one history entry. The local Vim register can also hold an ordered forest snapshot and original source IDs. Subtree puts allocate fresh IDs; the store rejects a put into a descendant of a still-present source node before mutation. The source IDs are used only for this runtime ancestry check. Structural repeat retains one bounded descriptor with a source snapshot when needed and reissues application commands from the current node; a count performs independent commands. Case changes traverse the selected subtrees, and range replacement adjusts cached attachment multiplicities from the removed and inserted subtrees. No selection or repeat state is persisted or sent across IPC.

`selectedSubtreeRowRange` in `visible-rows.ts` extends the highlight through the final selected root's visible descendants. It reads the flattened visible rows it is given and runs only during node Visual selection. `vimForestClipboardContent` exports selected trees in preorder with four spaces per level, including collapsed descendants. Single leaves retain the text/image preference. Export costs O(selected text plus indentation), retains no cache, and causes no document writes or syncs. `vimYankClipboardContent` uses that forest export for Normal `yy` on text, including counted forests. It retains the image-caret and empty-text-leaf rules. Normal `dd` keeps its separate single-node projection, so changing yank payloads does not alter deletion behavior.

Performance assessment (PRODUCT.md §22.1): text-object calculations scan only the active node text. Node Visual endpoints and the repeat descriptor are constant-size state apart from one captured subtree forest, bounded by the most recent register or repeatable put. Computing a selected sibling interval scans the current displayed level; highlighting compares indices for mounted rows, so ordinary typing outside Node Visual mode does not gain a list scan. Bulk commands traverse only selected subtrees plus the copied sibling array and ancestor path; repeated puts scale with the requested count and copied forest size. A command produces one history snapshot and the ordinary autosave scheduling, with no direct disk writes or syncs of its own. The wide-list Node Visual performance guard checks interactive selection latency and mounted-row bounds.
