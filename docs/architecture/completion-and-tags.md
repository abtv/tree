# Completion, Dates and Tags

### 8.8 Completion, Dates and Tags

#### 8.8.1 Completion Sources, Controller and Popup

`natural-date.ts` owns calendar interpretation without UI dependencies, including the three adjacent-month anchors and both labeled interpretations of ambiguous `next/last mon`. The pure renderer `completion-sources.ts` adapts prepared tag matches, then calls the emoji and date recognizers. Literal tag ranges cannot fall through to date completion. Each source produces shared suggestions: a stable ID, replacement text, primary label and secondary description, plus the list label, preferred suggestion ID and whether refinement retains selection. Date IDs combine calendar day and full interpretation so equal dates with different meanings keep distinct rows. Date rows are sorted chronologically; their preferred ID comes from the domain's first candidate, independently of display position.

The pure `completion-controller.ts` retains the semantic ID first, then the same replacement date if its former interpretation disappears; otherwise it selects the source's preferred ID. Emoji and tags reset to their first candidate on refinement. The controller owns one transient popup match, selected suggestion and shared dismissal transitions.

`use-completion.ts` obtains tag candidates from the store, adapts the shared Tree/Agenda input bindings and observes mode, composition, selection, editor context and external store changes; only a qualifying edit may open the popup. `CompletionPopup.tsx` presents that state without taking focus. Geometry lives in `editor-dom.ts`: rich inputs use DOM ranges, while textareas use a temporary measurement mirror with the input's font and wrapping. The hook reconciles popup state after pending caret restoration, preventing React's intermediate rich-text selection from dismissing it. When decorations replace a textarea with a rich element, the completion adapter transfers its element reference through the input registration path before caret reconciliation. Acceptance sends the replacement text, canonical date text or the full emoji sequence through the standalone `EditorStore.replaceTextRange` and the pending-caret owner.

Performance assessment (PRODUCT.md §22.1): recognition scans only the edited node's text; popup observation measures one active input and does no document traversal. The owner retains one node-sized text value and the current suggestion list; dismissal releases them, and temporary textarea mirrors are immediately removed. Popup changes cause no disk writes, syncs or undo snapshots. Acceptance performs one ordinary range edit and save scheduling; the editing performance guards cover the shared path. Input binding callback identity remains stable across focus-only changes.

#### 8.8.2 Date Recognition and Decoration

Date recognition is domain-owned: `findDateLikeTokens` and `findCanonicalDates` in `date-recognition.ts` return token ranges, and `date-decorations.ts` turns them into `TextDecoration` ranges for Tree and Agenda (PRODUCT.md §§20.10–20.11). Tree reuses Agenda's active-date styling for every canonical date. A Tree row keeps its plain `<textarea>` until its text contains a canonical date or a resembling token; it then renders through the rich `NodeInput` path that links use, and keeps that element for as long as the row stays mounted, so a focused row is never swapped back while typing. `NodeInput` records the textarea's focus and selection from its events and restores both in a layout effect when the element is replaced. The hide-under-caret rule is an attribute toggled on the invalid-date spans by `updateDateLikeUnderline`, called from the shared `selectionchange` and `focusout` listeners and, for the focused input only, after each commit; it causes no React render.

Performance assessment (PRODUCT.md §22.1): date recognition scans one node's text per render of that node; the caret rule measures only spans inside the focused input. Date recognition, decoration and the caret rule cause no document traversal, disk write, sync or history entry and retain no document state. Decoration arrays and spans are bounded by mounted node text and released on unmount.

#### 8.8.3 Emoji Completion

Emoji completion shares the `CompletionController` owner, input adapter and popup; it has no second input lifecycle. `emoji-completion.ts` recognizes shortcode fragments independently of UI and reads the bundled, attributed `emoji-catalog.json`. `completion-sources.ts` maps each emoji to its sequence as replacement and label and its `:shortcode:` as description. The emoji lookup checks the active node fragment against the fixed catalog and retains every ordered-subsequence match. The domain ranks contiguous match groups before fuzzy alignments; dynamic programming selects each fuzzy name's best alignment in query-length × shortcode-length time.

Performance assessment (PRODUCT.md §22.1): catalog storage is fixed, recognition does not traverse the document, and transient state is one active node-sized text value plus a catalog-bounded suggestion list and alignment workspace. §8.8.1 states the write and acceptance costs of the shared popup. Domain timing guards and the Electron emoji-completion scenario cover catalog browsing and fuzzy refinement.

#### 8.8.4 Tag, People and Event Catalogs

`tags.ts` recognizes case-sensitive literal tags and caches direct ranges by weak immutable-node keys. `TagCatalog` is a domain-owned derived index with one application owner in `EditorStore`. The runtime's before-publication callback updates it for every document replacement, including history restoration. It retains only the current document, node references, occurrence counts, sorted names and character membership buckets. Reference-equal subtrees are skipped; differing sibling arrays are compared, and changed text is parsed once. Character buckets narrow candidate lookup before the shared `completion-ranking.ts` ranks matches. Numeric alignment workspaces avoid per-character allocation during fuzzy lookup. Queries overlay the edited node's native draft and exclude its active occurrence without mutating the document or copying global counts.

People and event text markers reuse the tag recognizer and `TagCatalog`, parameterized by `#`, `@`, or `&`. The store keeps one derived catalog per prefix; immutable node recognition caches are weak and prefix-specific. Index updates reuse unchanged subtrees. Markers have no marker records, persisted indexes or subscriptions, and they cause no document writes or syncs. CPU and memory cost equals the tag complexity for each of the three namespaces; mixed-catalog scale guards cover this work.

Tag decorations join Tree and Agenda date/search decorations and use the shared rich-text selection mechanics.

Performance assessment (PRODUCT.md §22.1): tags have no persistence fields or history records and cause no direct writes or syncs. Initialization and structural replacement scan affected nodes; ordinary edits parse changed node text and compare references along copied ancestor/sibling paths. Catalog membership changes update character buckets and sorted names; count-only changes retain them. Memory is bounded by current nodes, tag occurrences and distinct name characters, plus weak node caches and one maximum-name-sized ranking workspace. Suggestion retrieval is independent of document node count once indexed, but scales with candidate tag count and name length. Automated guards cover 10,000 distinct tags, wide-document edits and real Electron typing; popup rendering is measured separately from the list-retrieval budget owned by the domain performance guard.

### 13.1 Emoji History

`EmojiHistory` owns the application-wide bounded shortcode MRU, outside document snapshots and Undo. Domain helpers normalize known unique shortcodes and prepare a cached initial catalog order when history changes; the history does not affect the ranking of nonempty emoji queries. The completion adapter supplies this order to the shared Tree/Agenda controller and records explicit emoji acceptance. The store loads history before publishing ready state and drains serialized asynchronous preference writes during its persistence flush. Failed writes remain dirty for retry and report through the operation-error surface. Desktop uses trusted, validated IPC and atomic replacement of `data/emoji-history.json`; browser uses the guarded `preferences/emoji-history` key. This preference is independent of notes replacement and archives, like command history. PRODUCT.md §20.12 specifies the performance costs and bounds; the history causes no document traversal and no per-keystroke history write.
