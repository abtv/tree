# Search

### 4.2 Search Modules

#### 4.2.1 Text Matching and Scope Traversal

`text-search.ts` provides incremental literal matching and query preparation. Unicode simple case equivalence preserves original UTF-16 spans without text normalization or full-text case conversion. The matcher compares code points. Comparisons between two ASCII characters fold letter codes directly; any non-ASCII character retains Unicode regular-expression equivalence, including folds across the ASCII boundary. A regular expression resolves each such pair of code points once; later comparisons read a bounded table of 256-code-point pages keyed by the query code point (at most 4096 pages, about 1 MiB, then the table starts over). The table holds code-point pairs only, no document text and no query. A streaming prefix matcher emits a forward, nonoverlapping match stream; reverse navigation selects from that same stream. The matcher yields one checkpoint per eight units of matching work (compared characters and prefix fallbacks), so a scheduled slice of 8192 checkpoints matches at most 65,536 characters.

`search-scope.ts` traverses Tree with a depth-sized stack, including the current-parent heading. Agenda traversal consumes an immutable projection supplied before fold filtering and keeps day/node occurrence identity. It builds a temporary node-reference map incrementally; it neither copies node text nor retains a text index. Projection derivation is the Agenda owner's responsibility.

#### 4.2.2 Search Executor

`search-executor.ts` schedules bounded scan slices through an injected scheduler. Count stops at match 101. A completed exact local count retains up to 100 ordered match spans with occurrence identities, row ranks and references to the existing text, plus the captured origin's row if present. The search session releases them when its count is invalidated or search is hidden. Confirmation reuses a completed count for the same query. If that count is still running, confirmation keeps it and starts the first jump when it completes, so one scan serves both; a navigation scan running beside the count would compete with it and, on a large document, arrive about twice as late. A repeat from hidden search likewise starts after the count that restores its feedback; that count records the repeat's origin row. A repeat while a recount runs, for example after an edit, also waits for it. Jumps from the captured origin, a match or a day heading resolve from the saved positions. A manual move to another row may require an incremental occurrence walk to locate its rank.

For a capped count, navigation retains the two most recent blocks of up to 64 matches and their ranks. In Tree, the first full navigation scan also collects up to 8192 ordered match positions for the active query. If they all fit, a repeat from a cached origin can load the block around any destination directly by rank. At match 8193 the executor discards the full collection and uses the same two-block strategy as Agenda. The session releases these positions on the same events as the exact spans.

A repeat from a cached origin to a retained destination uses the same modular rank calculation and schedules a cancellable microtask. A repeat started while a cached result is being published uses an ordinary scheduled task instead, so input and painting can run between queued deliveries. When a scan from a real occurrence already knows the total, it can stop after collecting 32 matches past the origin. If the destination was not retained, a second pass locates it by rank.

Only the selected destination invokes native grapheme segmentation, inside its scheduled callback. JavaScript matching and traversal have explicit checkpoints; a native ICU segmentation call is indivisible, so oversized ordinary, combining and emoji text have measured performance guards rather than a claimed universal time bound. Cancellation releases active scan state and suppresses queued delivery.

The default scheduler uses cancellable `scheduler.postTask` tasks at `user-visible` priority where supported, with zero-delay timers as the fallback. This avoids nested timer delays without changing the fixed checkpoint limit. Integrated Electron measurements on large documents confirmed lower completed-search CPU time and elapsed time; rapid cancellation can consume more CPU because more work runs before cancellation. These measurements do not establish improved input latency or power consumption.

Count and navigation jobs perform no persistence work; §4.2.5 states what applying a destination persists. `perf/electron/node-search.spec.ts` guards complete scans of large ASCII and Cyrillic documents. `perf/electron/search.spec.ts` guards repeated navigation, deep and wide scopes, long mounted text, cancellation retention and current-result latency separately from animation-frame scheduling latency. Its task probe includes native posted tasks and all zero-delay timer callbacks in the measured phase, without attributing every callback to search. Animation-frame timings do not establish physical display presentation.

#### 4.2.3 Search Session

`search-session.ts` owns memory-only query recall, draft entry, feedback and request validity. Its local mode is hidden, editing (with the captured origin and cancellation visibility), or confirmed. The public snapshot is a cached projection of that mode and count feedback. Count and navigation have independent idle/running jobs and separate request IDs, and share context invalidation; only confirmation keeps a running count of its own query. A jump that waits for a count is discarded by the same invalidation, an interruption or a newer jump; a confirmation without a jump of its own keeps one that a subscriber queued for that count. These bounded runtime records need no traversal or disk work. The caller must replace context before publishing a new document revision or presentation scope. Late callbacks are rejected even if an executor ignores cancellation. A pending navigation can be superseded; the input owner must serialize repeated user intents after applying the previous destination, and retry canceled navigation only against a fresh context. Raw match offsets and grapheme caret offsets are separate; subsequent navigation can preserve the raw match anchor while the caret remains at its containing grapheme.

#### 4.2.4 Find Controls and Focus

`use-local-search.ts` coordinates shared Find shortcuts and pointer controls with the application search session. Agenda exposes its current read-only caret through its renderer owner; `EditorStore.searchOrigin` resolves occurrence or synthetic origins. Native Find menu commands use a validated main-to-renderer notification; command-panel actions call the same renderer entry points. These controls retain bounded session-only references and do no document-scale work or persistence themselves; §4.2.5 states what search navigation and closing Find persist.

The renderer presents the same session as a Find panel in standard editing and a bottom status-bar prompt in Vim. Vim confirmation returns focus through the search-focus owner; confirmed feedback contains no editable field. While Find owns focus, navigation updates selection and reveal without focusing an editor or writing its native caret. The input bindings delegate search focus policy to the DOM-independent `SearchFocusController`, supplying live search and DOM focus observations without changing their ordered commit pipeline. The controller retains one deferred focus intent for close/Escape; genuine editor focus invalidates that intent so a later restoration cannot replace a newer manual selection.

#### 4.2.5 Editor Search

`editor-search.ts` connects Tree and Agenda input through `EditorStore`. Runtime publication updates its monotonic document revision, including Undo/Redo, before notifying subscribers. Scope identity stays stable across ordinary selection and folds. The controller serializes navigation and retains the raw match anchor separately from the grapheme caret. Repeated jumps belong to the active navigation queue. An interruption or a jump without a destination discards its remaining repeats. If a subscriber starts a new jump while search becomes visible, only the new jump can move the caret.

`EditorSearch` resolves origins, reveals ancestors and restores search-owned folds, including manual Tree/Agenda fold ownership transfers. Search-owned Tree folds belong to the active expansion view. Before `EditorRuntimeState` installs a snapshot, `EditorSearch.closeFoldsLeavingScope` closes them as Escape does when a Tree location change, opening Agenda or a star change that switches the view ends their scope, keeping the path to the selection of the view being left; it runs after Agenda reconciliation, which can move the displayed week, and before view activation, so a starred view that copies its expansion never inherits them, and closing Find never closes a fold of another view. Agenda week and focused-day changes close Agenda search folds the same way, including in the remembered timeline return; returning to that timeline only ends ownership, since the focused day's folds end with it. A node-text click hides search through `hideSearchAtPointer` without folding, so rows stay under the pointer; ownership remains until one of those changes. It returns explicit Tree or Agenda view changes with a target location and token-free focus for a reveal. `EditorStore` publishes those changes, creates focus tokens, ends the text session before Agenda reveal, and schedules Tree view persistence. Search disposal cancels work without changing the view. This keeps fold policy with its ownership set and publication effects in the store. The returned view change is a short-lived result.

Query entry suppresses document focus projection while keeping ordinary selection authority current underneath. For local search, mounted inputs compute ordinary highlights with the query during render. A bounded text-plus-query length keeps oversized work on the cancellable incremental path. The renderer composes these ranges with link, date and caret intervals.

Agenda reuses the store-owned direct-match projection cache before day-fold filtering. Scope keys include the Agenda root and focused day and displayed week. Projection changes, including leaving a pinned item without a document edit, invalidate results. The editor store reports a committed focus token to the search owner. Its jump notification lets the renderer finish the active editing session even when the same move starts a recount. Manual input interrupts the pending navigation before native selection or composition changes, with constant work on an idle search. Origins and anchors retain occurrence day; synthetic headers use a position before their day. Read-only rows consume the focus token for same-row caret arrivals and its optional line-reveal hint to reveal a search destination within wrapped text. Agenda reveal/cleanup uses day-fold keys without changing Tree expansion.

Performance assessment (PRODUCT.md §22.1): inactive search performs no corpus scans. Query entry, counting and highlighting perform zero writes or syncs; navigation uses view-state persistence in Tree, and the store's save snapshot asks `EditorSearch.persistentExpansion` for the Tree folds Escape would leave, so revealed folds stay runtime state; closing Find that folds rows still marks a save, because the selected row's measured position changes; Agenda search navigation and temporary fold reveals are runtime-only and cause no writes or syncs. Per execution, memory scales with query length and traversal depth; Agenda additionally holds one temporary node-reference map proportional to document size. Session replacement and cancellation release obsolete work; memory does not grow with edit history or completed request count. The application and domain search modules have no persistence fields and use no IPC, Worker or external dependency.

### 13.3 Search Results and Sessions

#### 13.3.1 Result Shape and Navigation

`node-result.ts` owns the Search result shape and its label, path and presentation helpers, which Search, the marked and starred list and Agenda paths share. The Search popup borrows editor focus and dispatches the store's `openSearchResult` navigation command; it does not mutate document content. The application keeps no history of edited or visited nodes. A `data/recent-nodes.json` file or a browser key `preferences/recent-nodes` that an earlier version saved is never read, written or deleted, so it stays as it was.

#### 13.3.2 Document Matcher, Suggestions and Highlights

`node-search.ts` owns complete-document result enumeration for Search. The domain `node-search-query.ts` prepares whitespace-separated terms with independent smart case, reuses streaming KMP for ordinary substring terms, and matches complete recognized marker names excluding links. A depth-first traversal tracks per-term match counts on the current ancestor chain and the terms matched by each entered node; leaving a branch removes only that branch's contributions. A result requires every term to be covered and at least one term to match locally. Ancestor text is not rescanned for descendant eligibility, and no document-wide text index or normalized text copy is retained. Matching costs scale with query terms and scanned node text; transient coverage storage is bounded by query size and traversal depth, in addition to results and the recognized-tag caches. The query matcher collects marked, starred and other matches separately during its depth-first traversal and returns the marked matches first, then the starred matches, then the others.

The store forwards every nonempty query to that matcher. The popup session requests catalog suggestions for the marker term at the caret, including within a multi-term query; accepting a suggestion replaces only that term. Global suggestions require continuous case-folded name matches; inline completion keeps its separate fuzzy matching. `tag-search.ts` shares Unicode folding and source-offset projection with suggestion highlighting. Scheduled batches yield to input; cancellation releases obsolete generators and their snapshots. Result titles retain the original full text by reference. The application projection supplies recognized marker-match ranges excluding links, including mapped offsets in bounded, whitespace-normalized ancestor labels. The renderer combines those ranges with ordinary-term matches through `nodeSearchHighlights`, applying independent smart case and merging overlapping ranges. Hidden image text affects eligibility but supplies no visible highlight ranges. The input/completion session stays separate from Vim search and document undo. Searching performs no persistence operations; confirming a result uses the `openSearchResult` navigation transition, which marks a persisted change for the idle autosave. Application scale guards cover inherited multi-term queries, alongside the real Electron node-search scenarios.

#### 13.3.3 Popup Session and Result List

`global-search-session.ts` is the pure renderer-local owner of the Search popup's current query, completed results, pending work, selection, tags and composition. The session publishes this state as one subscribed snapshot, which the popup reads instead of parallel React state. It invalidates obsolete callbacks and closes before returning a chosen result, so finishing a buffered edit cannot reopen Search through document publication. Keyboard and pointer visits share that transition. `GlobalSearchPopup` adapts input and document notifications, restores focus, and owns DOM measurement, scrolling and the rendered row window. The session reuses the store's marked and starred list, tag and search functions; it has no index, document scan, history or persistence write of its own. Retained memory is bounded by the current displayed results and one active request, released on close.

The popup windows measured, variable-height rows using the shared list-offset helpers. `search-result-window.ts` counts node and heading options, reserves all intersecting entries and the offscreen selection, then uses the remaining PRODUCT.md §20.14 budget for overscan. The popup caps the list height using the shared minimum row height and reserves room for partially visible entries and the pin. Unknown heights use an estimate; ResizeObserver measures mounted rows and width changes invalidate offscreen measurements. Offset changes preserve the current scroll anchor. A zero-height sticky anchor retains painted results until the native scroll handler synchronously replaces rows and their relative offset. The total-height container clips overflow. Query, completion, composition, refresh and opening reset scrolling; selection reveals the row or its first match when oversized, without changing result-session ownership. The budget check works over the intersecting entries and a bounded number of spare entries. Measured heights and offset arrays scale with current results. Highlight scanning reuses the yielding literal-decoration hook; tag ranges come from the application projection. Result windowing performs no document writes or syncs and uses no animation-frame polling. Search scale scenarios and native scroll/frame regressions guard these costs.

The renderer groups consecutive nested results by parent ID and displayed path. A measured entry contains the node and its optional group heading. Either can receive the selection frame. The counter uses the node's index for both positions, so headings add no results to the total. Its reserved width comes from `EditorStore.searchResultCapacity()`, the document's node count; `src/application/node-count.ts` caches counts per subtree in a weak map, so a repeated count visits only top-level nodes and the changed path of an edit. Each node option exposes its path as an accessible description even when the heading is outside the rendered window. A result carries its node's attachment ID and stored natural size; `AttachmentThumbnail` in `AttachmentPreview.tsx` loads it through the bounded decoded-image cache shared with Tree, so only mounted rows decode thumbnails. The list's flex basis uses the measured entries without the conditional trailing inset, so adding scroll space cannot resize the viewport and repeatedly toggle its own overflow condition. The node-search scale scenario covers the measurement and scrolling cost.

#### 13.3.4 Marked and Starred Entries

`starred-nodes.ts` derives empty Search entries on demand: marked starred nodes, then the other marked nodes, then starred nodes that are not marked. Each part keeps document order from one depth-first traversal, without sorting, and results are cached by immutable document in a weak map. A timing guard groups 6000 flagged nodes. Weak node summaries prune unchanged branches after edits; this preparation never runs on text input. Memory follows reachable documents/nodes and their marked and starred results. No other entries are added and no history is stored. Search keeps consecutive parent-ID grouping and its nonempty-query executor.

### 21.2 Editor Store Search Interface

`EditorStore.search` exposes search commands and read-only session observation, while context replacement and fold ownership are private store operations. Renderer unmount calls `disposeSearch` to retire search without changing folds; the user close command is `hideSearch`, which also releases search-owned folds. This typed view exposes the search owner itself, not a separate object; it holds no subscriptions, document scans, writes or retained snapshots of its own. Its `navigate` and `confirm` commands reach the store's reveal, which marks a persisted change for a Tree destination (§4.2.5).
