# Renderer Interaction State Ownership

## Objective and authority

Remove the design cause behind the repository's four recurring renderer defect clusters: renderer interaction state and its visual representation have no single owner, so the same fact is re-derived and re-written at each call site and a new path can miss one. The Product Owner requested this analysis and authorized creating this plan; implementation of each task requires a Product Owner request to continue.

Every task is a behavior-preserving refactoring or a documentation correction. No task may change user-visible behavior. Product behavior is owned by [Product Requirements](../docs/PRODUCT.md), the interaction architecture by [Architecture](../docs/ARCHITECTURE.md), the navigation and caret test contract by [Development Guide §8](../docs/DEVELOPMENT.md#navigation-and-caret-changes), validation tiers by [Development Guide §9](../docs/DEVELOPMENT.md#9-full-validation), and requirement-to-test mapping by [Vim Conformance](../docs/VIM_CONFORMANCE.md). Those documents take precedence over this plan.

## Boundaries

* Preserve specified behavior, the document and persistence models, and process boundaries. A task that reveals a genuine defect must reproduce it and add a regression test before fixing it, per `AGENTS.md` §9.
* Keep new owners pure and renderer-local, following the existing `vim-caret-transition.ts` pattern. A larger architectural change needs Product Owner approval.
* Any stylesheet, caret, selection, or drag-feedback task must be pixel-identical unless the Product Owner authorizes a visual change. Follow the visual-regression workflow in `AGENTS.md` §9; do not accept a regenerated screenshot baseline without deliberate inspection.
* Do not delete an end-to-end case to reduce cost. Cost is addressed by OWN-3 (file split), not by removing coverage.
* One task per session and per commit. Update this plan in that task's commit.

### Resolved

**D1 — one highlight token pair per appearance. Decided by the Product Owner on 2026-09-27.**

The question as originally written was based on a misreading and is void: `#fff0b3` and `#f5e9b7` are not competing light-mode highlights but a background and foreground split across appearances. Light mode uses background `#fff0b3` with text `#373f43`; dark mode uses background `#4a4023` with text `#f5e9b7`. Exactly one highlight color per appearance already exists.

The real duplication is that this one pair is repeated across four surfaces: `.node-row-visual-selected`, `.vim-state-visual .node-input::selection` together with its hand-written `a::selection` twin, `.vim-state-visual .node-input a.link-selected`, and `.vim-mode-visual`/`.vim-mode-visual-node`. Commits `0af7309` and `e81e885` exist only because those surfaces drifted apart. The Product Owner's decision is that all four share a single highlight token pair, so a later change to the highlight moves the mode badge with the selection rather than leaving it behind. Do not introduce separate per-surface tokens that merely hold the same value.

One asymmetry to normalize while tokenizing: `.node-row-visual-selected` sets only `background` in light mode and inherits its text color from the `:root` rule, which is the same `#373f43` the other three set explicitly, while its dark-mode rule does set `color` explicitly. Making the token pair explicit on all four surfaces in both appearances is pixel-identical. OWN-4 therefore requires no visual change and no further Product Owner decision.

## Findings behind the task order

The four clusters were identified by classifying all 62 `fix` commits by theme: Vim caret, image, and session state (17 commits, partly addressed by the completed Vim initiative), node drag against caret and selection (9), selection and caret styling (8), and hyperlink caret and selection (9). Seven of the styling commits are named "match" or "align" and exist only to synchronize a duplicated value, which is the clearest evidence that the cause is duplication rather than missing tests. Global coverage was 95.58% while these defects were being introduced, so coverage is not the lever; the weakest per-file coverage sits exactly where the clusters are, because state inside a React hook can only be reached through React Testing Library or Electron.

Order rationale: OWN-1 to OWN-3 are mechanical, carry the least risk, and make the documentation truthful and the suite cheap before any refactoring. OWN-4 to OWN-6 move outward from tokens to the hyperlink owner, so each has a stable base. OWN-7 to OWN-9 continue the proven `vim-caret-transition.ts` extraction pattern into the remaining state. OWN-10 guards the outcome.
