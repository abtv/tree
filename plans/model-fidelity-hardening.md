## Findings that shape the work

* No automated test asserts PRODUCT §2.4's "no undo entry or save" for inline expansion. Searches of `src/renderer/App.test.tsx`, `e2e/inline-expansion.spec.ts`, `e2e/undo-sessions.spec.ts`, and `e2e/history.spec.ts` find nothing. The behavior is believed correct (fold commands only call `setExpansion`, and only `zM`'s collapse-hides-caret selection change persists the location, which is ordinary selection behavior), but nothing guards it.
* `createEditorKeyDownHandler` detects composition only through the React `composing` state set by `onCompositionStart`/`onCompositionEnd`. The keydown that starts composition can arrive before `compositionstart`, so it can still be read as a Normal-mode command. The native signal is `KeyboardEvent.isComposing` on `event.nativeEvent`; Chromium may also report `key: 'Process'` and `keyCode: 229` for IME-consumed keydowns.
* `isNeutralKeydown` covers `Shift`, the lock keys, `AltGraph`, `Dead`, and `Compose`, but not `Process` or `Unidentified`.
* Auto-repeat is never modeled: tests always tap a key, while hardware repeats keydowns. Prefix and awaiting keys (`z`, `r`, `g`, and operator keys) change state on each repeated keydown. The intended behavior is that a repeat is an ordinary repeated keypress, but no test pins that.
* Renderer tests build `EditorStore` mocks as unchecked assertions (`as unknown as EditorStore`): 29 occurrences in `src/renderer/use-node-input-bindings.test.tsx`, one in `src/renderer/editor-input-handlers.test.ts`, and three in `src/renderer/vim-interaction.property.test.ts`. A missing or renamed store member does not fail typecheck, so a double can silently diverge from the real interface — the same failure mode [ADR 0014](../docs/decisions/0014-single-owner-for-renderer-interaction-state.md) removed for the Vim keyboard state.

Baseline: commit `92a7bfd`, clean worktree; the full unit suite is 72 test files, and `npm run check:full` passed on the preceding fix.

## Decisions and findings for later sessions

* Items 2 and 6 are excluded by the Product Owner on 2026-09-28. Do not add AltGr/Option key handling and do not change the viewport behavior of fold commands. If item 2 is ever revisited, it needs a manual non-Latin/AltGr layout probe and a product/input decision first; item 6 needs a product decision about scrolling the caret into view.
* Repeat handling adds no special case: a repeated keydown is an ordinary repeated keypress, and MFH-4 only pins that behavior.
* `isNeutralKeydown` is the single place listing keydowns that are not commands; new findings extend that set and the neutral-key `it.each` table, not per-command checks.
* Real IME behavior is the one dimension this initiative cannot execute at the real boundary; MFH-2/MFH-3 use unit-level contract sequences and must say so in their handoff. Do not claim IME E2E coverage.
