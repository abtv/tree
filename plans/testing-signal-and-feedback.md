# Testing Signal and Feedback Initiative

## Objective and authorization

Assess whether the test suite and validation workflow find meaningful defects promptly without making routine changes unnecessarily slow. The Product Owner requested analysis and a durable plan on 2026-09-28, and explicitly requested **no implementation changes in that session**. This plan records proposed follow-up work; no test, runtime, threshold, or validation-policy change is authorized for the planning session. A later request to continue this initiative authorizes its next ready task within the boundaries below, under [AGENTS.md](../AGENTS.md) §8.

Keep current product behavior and mandatory validation gates until evidence supports a specific adjustment. Do not raise global coverage floors merely to improve a percentage, remove boundary or visual checks, refactor renderer state without a demonstrated cause, or change the technology or persistence model. The source requirements are [PRODUCT.md](../docs/PRODUCT.md) §§2.1, 2.4, and 22, [ARCHITECTURE.md](../docs/ARCHITECTURE.md) §§9–10, and [DEVELOPMENT.md](../docs/DEVELOPMENT.md) §§8–12.

The report does not include Electron end-to-end execution. These timings are one local observation, not a workflow baseline.
- The last 50 commits contain a large inline-expansion feature spanning domain, application, renderer, Electron tests, and performance tests, alongside many Vim interaction fixes and ownership refactors. Inline expansion already has focused and property tests, 13 Electron scenarios, and a scale guard. Its pure `visible-tree.ts` and `expansion-state.ts` modules have complete unit branch coverage. The two subsequent alignment fixes concerned real-renderer geometry and focus appearance; a higher unit branch floor would not have detected those pixel relationships. The new geometry and screenshot checks now guard them.
- [PRODUCT.md](../docs/PRODUCT.md) §2.4 says reopening the application starts with nodes collapsed. The expansion Electron spec covers entering and leaving locations but has no explicit expand–quit–relaunch assertion, and a repository-wide search found no other expansion/reopen case. This is a specific process-boundary coverage gap to verify and close. It is not evidence of a known implementation defect.
- `NodeList.tsx` has about 79.8% unit branch coverage and `use-node-list-drag.ts` about 81.1%, but many existing unit and Electron cases already exercise windowing, focus, drag, and expansion. The uncovered branches need semantic inspection before deciding whether another test is valuable. TSF-2 completed that audit; the classification and decisions are in the TSF-2 audit results section below.
- `npm run check:full` adds real Electron E2E and serial visible performance suites to `npm run check`. [ADR 0012](../docs/decisions/0012-parallel-e2e-execution.md) measured a roughly 55-second hidden E2E run after parallelization, but that is historical and does not measure the current full gate. [DEVELOPMENT.md](../docs/DEVELOPMENT.md) §10 already has a blank three-product-outcome workflow-speed pilot. Use it rather than creating a second timing policy. The expansion outcome occurred after that pilot was introduced but was not recorded at the time; the Product Owner later directed that it be entered as slot 1 with its human-observed values explicitly not captured (see TSF-3 pilot observations). Record the next product outcomes as they complete and explicitly check pilot recording at each handoff.
- While validating TSF-1 at `d275b84`, the focused E2E spec and a diagnostic full `npm run test:e2e` exposed 7 pre-existing screenshot-baseline failures, each exactly 25 pixels, all in the selected-node focus marker. The cause is `4f3f365`, which moved `.node-focus-marker` from `top: 8.5px` to `6px` without regenerating any existing baseline containing the marker; the current rendering itself matches the intended `docs/PRODUCT.md` §2.1 alignment. `npm run check` excludes E2E, so the standard gate stayed green and the stale baselines landed. Each failing test stops at its first light baseline, so its dark variant and any other marker-bearing baseline may also be stale; 16 baselines were affected in total. The Product Owner authorized the refresh on 2026-09-28; the baselines were regenerated with `playwright test --update-snapshots`, every image was deliberately inspected against the intended §2.1 alignment, and the full E2E suite then passed 273/273 in a separate test-artifact commit.

## TSF-2 audit results

Audited at `df81a2c` with `npm run test:coverage` (72 files, 1,048 tests passed after the additions). `src/renderer/use-node-list-drag.ts` rose from 91.16% statements / 81.13% branches to 95.02% / 87.73%; `src/renderer/NodeList.tsx` stayed at 76.22% / 79.8% and `src/renderer/node-drag.ts` at 100% / 98.61% because the remaining paths there are defensive or platform wiring. Three focused cases were added to `src/renderer/NodeList.test.tsx`:

* a pending hold cancels when the pointer leaves the pressed row without exceeding the 4px hold tolerance (`docs/PRODUCT.md` §11);
* a pending hold never arms and is cancelled when windowing unmounts the pressed row before the hold fires; the uncovered code would otherwise read bounds from a missing element (`docs/PRODUCT.md` §§20.1 and 21);
* an active drag survives a release from another pointer, another pointer's lost capture, the source row's hover reset, and ordinary keys, and still commits on the owning pointer's release; only the owning pointer and `Escape` end it (§11).

The windowing case was mutation-checked: bypassing the hold guard in the source makes it fail (and only it), so its assertion is tied to the guarded transition rather than to incidental rendering.

Classification of the paths kept without a new focused test:

* defensive or unreachable fallbacks in `use-node-list-drag.ts`: dataset-index and zero-height row guards, missing source row or empty boundary list, missing regions or boundaries on move, release, and recompute, and a null list ref;
* pointer-capture feature detection and `try`/`catch` in `use-node-list-drag.ts` (the success path runs only in the real renderer, exercised by `e2e/drag-and-drop.spec.ts` and the windowed auto-scroll drag in `e2e/windowed-list.spec.ts`);
* `NodeList.tsx` ResizeObserver measurement and window-width height invalidation: presentation/platform wiring already covered in the real renderer by `e2e/windowed-list.spec.ts` (wrapped-text and attachment row growth, row tiling, and the window-resize re-wrap test); a jsdom case would drive a stub of the platform API;
* `NodeList.tsx` defensive fallbacks: unobserved-element unregistration, null list ref in `updateViewport`, windowed offset `?? 0` and row-undefined guards, and the `drop-zone-edge` false class that both call sites make unreachable;
* `node-drag.ts`'s `previous === undefined` fallback, which the topmost/bottommost guards make unreachable.

Unchanged-selection behavior already has focused coverage (`releases without a position change and commits nothing`, the duplicate-press case, and the E2E dragged-selection test), so no addition was made. No coverage threshold changed, and no runtime source or shared fixture was touched.

Measurement note for TSF-3/TSF-4: two consecutive `npm run test:coverage` runs on identical test inputs differed by one statement in `vim-editing.ts` (99.37% versus 98.75%; the drag modules were stable). Treat single-run global coverage deltas of one or two statements as seed-dependent measurement noise, not as a regression.

## Decisions and boundaries for future sessions

The present recommendation is **targeted coverage and measured feedback**, with existing thresholds retained. TSF-1 and TSF-2 may add tests for existing requirements. TSF-3 gathers evidence through ordinary authorized product work; this plan does not itself authorize those product changes. TSF-4 may clarify focused commands within existing gates. A proposal to lower or remove a mandatory gate, change CI platform coverage, accept a confidence tradeoff, or alter user-visible behavior requires a Product Owner decision before implementation. A runtime defect found during TSF-1 or TSF-2 must be scoped and validated as its own fix; do not bury it in test-maintenance work. Pilot slot 1 was entered retrospectively with `Not captured` values at the Product Owner's direction on 2026-09-28; the expectation that outcomes 2 and 3 be recorded as they complete is unchanged.
